db/oxiwire

Imported as import "db/oxiwire" as oxiwire, its names are then oxiwire.…. Every signature below is the one the checker infers.

OxiWire — the binary format OxiDB's native wire speaks, encoded and decoded in Rill.

The server picks its format from the first byte of a frame: { is JSON, 0xDB is this. There is no handshake and nothing to negotiate, so a client chooses per message simply by what it writes first.

A tagged encoding of the same values JSON carries, with every length and every number a fixed width so a reader never decodes a varint:

00 null 01 false 02 true 03 i64 04 u64 05 f64 — 8 bytes little-endian 06 string — 4-byte LE length, then the bytes 07 array — 4-byte LE count, then the values 08 map — 4-byte LE count, then (bare key, value) pairs

A map key carries no tag of its own: a 4-byte length and the bytes, because a key is always a string. That one asymmetry is the whole difference between reading a map and reading an array.

It is not smaller than JSON — fixed-width numbers see to that, and a reply of six hundred documents measured about a third larger. What it is is quicker to read: a length known in front means one str_sub where a parser has to look for where the value stops. About 1.4 times, end to end on a local socket, and it was 2.5 before json.rill's parser was fixed — most of what looked like the format's advantage was that parser's fault.

A request is 0xDB and a value. A reply is 0xDB, a status byte — 0 for an answer, 1 for a complaint — and a value. The reply is not wrapped in the {"ok":.., "data":..} envelope the JSON wire uses: the status byte is the envelope, which is one of the things the binary format buys.

Values are Json, so a document decoded here is the same kind of thing one parsed from text is, and to_string prints either.
